# Генерация синтетических данных

Генератор заполняет мигрированную PostgreSQL данными интернет-магазина. Имена составлены из встроенных списков, email используют домен `example.test`. Даты берутся из фиксированного периода в UTC. Пользователи и каталог появляются в 2023 году, заказы и события распределены по 2024–2025 годам с уклоном в более свежие даты. Часть пользователей и товаров встречается заметно чаще остальных.

## Профили

| Профиль | Пользователи | Категории | Товары | Заказы и платежи, по | Позиции заказов | События | Записи истории |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `small` | 1 000 | 20 | 100 | 10 000 | 20 000–40 000 | 50 000 | 20 000 |
| `medium` | 10 000 | 20 | 1 000 | 100 000 | 200 000–400 000 | 500 000 | 200 000 |
| `large` | 100 000 | 20 | 10 000 | 1 000 000 | 2 000 000–4 000 000 | 5 000 000 | 2 000 000 |

Профиль по умолчанию — `small`. `--users`, `--orders` и `--events` переопределяют соответствующие размеры профиля. Количество товаров составляет примерно десятую часть числа пользователей в пределах 100–10 000. На заказ приходится от двух до четырёх позиций и одна попытка оплаты. Начальный заказ в `pending` получает одну запись истории, а следующий заказ из той же пары получает три. Остальные заказы получают по две записи.

## Запуск

```bash
docker compose up --build -d --wait
docker compose exec api alembic upgrade head
docker compose exec api python -m scripts.generate_data --profile small --seed 42
```

Из локального Python используйте следующий вызов. Настройки PostgreSQL берутся из переменных окружения и `.env`.

```bash
uv run --locked python -m scripts.generate_data --profile medium --seed 42 --batch-size 5000
```

Загрузка идёт пакетами в одной транзакции. Размер памяти зависит от `--batch-size`. После загрузки генератор проверяет `COUNT(*)` во всех восьми таблицах, синхронизирует identity-последовательности и запускает `ANALYZE`. Прогресс записывается в stderr, итоговые параметры, счётчики и время выходят в stdout в виде JSON.

Повторный запуск с теми же параметрами сверяет число строк с записью в `lab_data.dataset_manifest` и возвращает `action: reused`. Для другого набора используйте пустую мигрированную лабораторную БД или явную очистку.

## Очистка с подтверждением

Команда очистки удаляет содержимое восьми таблиц и перезапускает их identity-последовательности. Она требует точного имени БД, локального хоста или сервиса PostgreSQL в Compose и совпадения числа строк с записью о сгенерированном наборе. PostgreSQL отклонит очистку, если на эти таблицы есть внешние ссылки из других таблиц. [PostgreSQL TRUNCATE](https://www.postgresql.org/docs/16/sql-truncate.html)

```bash
uv run --locked python -m scripts.generate_data --clear --confirm-clear performance_lab
```

## Сравнение COPY и INSERT

1. Для каждого прогона используйте пустую мигрированную лабораторную БД с одинаковой схемой и настройками PostgreSQL. Задайте те же профиль, `seed` и `--batch-size`.
2. Запустите генератор с `--strategy copy` и с `--strategy insert`. Первый режим использует бинарный `COPY`, второй выполняет пакетный параметризованный `INSERT`. [asyncpg API](https://magicstack.github.io/asyncpg/current/api/index.html#asyncpg.connection.Connection.copy_records_to_table)
3. Сохраните JSON каждого запуска. `load_seconds` включает генерацию и загрузку строк. `elapsed_seconds` дополнительно включает подключение, проверку числа строк, `ANALYZE` и фиксацию транзакции.
4. Сравните счётчики всех таблиц, повторите оба прогона несколько раз и сравните медиану `load_seconds` при сопоставимой фоновой нагрузке. Для общей пропускной способности поделите сумму `counts` на `load_seconds`.
