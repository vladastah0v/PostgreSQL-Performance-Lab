# Результаты профилирования FastAPI

## Что измеряется

Флаг `API_PROFILING_ENABLED=true` включает `Server-Timing`, `X-SQL-Queries` и `X-Worker-Pid` для маршрутов `/api/v1/`. `Server-Timing` передаёт длительности в миллисекундах. FastAPI сообщает длительность обработчика и валидации с сериализацией через локальный OpenTelemetry-провайдер. Провайдер записывает только длительности в контекст запроса. Данные трассировки остаются в памяти процесса. [Спаны FastAPI](https://fastapi.tiangolo.com/advanced/opentelemetry/#trace-request-operations)

| Показатель | Границы |
| --- | --- |
| `server` | От входа в ASGI middleware до отправки заголовков ответа. |
| `sql` | Сумма интервалов SQLAlchemy от `before_cursor_execute` до завершения выполнения, включая ожидание драйвера. |
| `pool` | Получение соединения, включая ожидание свободного слота, `pre_ping` и открытие нового соединения при необходимости. |
| `serialization` | Валидация модели ответа и кодирование JSON в штатном спане FastAPI. |
| `cache` | Работа с Redis и ожидание вычисляемой записи за вычетом чтения источника. |
| `logic` | Остаток времени обработчика после вычитания SQL, получения соединения и кэша. Включает материализацию результатов и сборку моделей. |
| `framework` | Остальной интервал до отправки заголовков, включая маршрутизацию, зависимости и обработчики ошибок. |
| HTTP latency | Время от вызова `httpx.get` до полного чтения тела. Остаток после вычитания `server` охватывает транспорт, Uvicorn и работу клиента. |

Клиент сохраняет размер тела ответа в байтах. SQL-события включают завершившиеся ошибкой запросы. Получение соединения остаётся ленивым, поэтому при попадании в кэш профиль может показать нулевые `sql`, `pool` и число SQL-запросов. [События SQLAlchemy](https://docs.sqlalchemy.org/en/21/core/events.html)

## Методика

Baseline и Optimized сравниваются на одном наборе и одной схеме `0002` с выключенным кэшем. Клиент прогревает оба варианта, чередует их порядок по волнам и сверяет хеши успешных JSON-ответов. В эксперименте пагинации получение опорной строки происходит до замера. Сравниваются содержимое страницы, порядок и `has_more`, при этом тело keyset использует `offset=0`.

В экспериментах пула используется один запрос продаж, четыре параллельных запроса в волне и по 20 измерений на конфигурацию. HTTP-соединения открываются заново для каждой выборки, чтобы запросы попадали в разные workers. Перед каждой конфигурацией скрипт проверяет `workers × (pool_size + max_overflow)` с учётом открытых соединений и резерва PostgreSQL. Ответы `503` при коротком таймауте учитываются отдельно, а JSON содержит задержки всех ответов и квантили успешных. [Настройки Uvicorn](https://uvicorn.dev/settings/#production)

В микрозамере ORM и Core выполняют одинаковый SQL для 1 000 пользователей на одном соединении и строят одинаковые `UserSummary`. Вычитание времени драйвера из длительности операции даёт интервал клиентской обработки, включая получение строк, материализацию и валидацию моделей. HTTP в этот замер не входит.

## Замеры на `medium`

Набор с `seed=42` содержит 100 000 заказов и 500 000 событий. Использовались PostgreSQL 16.16, два CPU Docker Desktop и лимит контейнера API в один CPU. В таблице показаны HTTP-квантили из 20 запросов на вариант с конкуренцией 4. [Сырые замеры и метаданные](../benchmarks/results/fastapi-medium-2026-11-24/latency.json)

| Операция | Варианты | p50, мс | p95, мс | p99, мс |
| --- | --- | ---: | ---: | ---: |
| История из 20 заказов | Baseline → Optimized | 213,36 → 83,27 | 295,08 → 117,33 | 308,83 → 152,18 |
| Рейтинг товаров | Baseline → Optimized | 1 520,66 → 709,32 | 1 698,45 → 896,67 | 1 725,60 → 1 211,16 |
| Страница на глубине 8 000 | OFFSET → keyset | 43,75 → 35,01 | 53,55 → 40,91 | 58,98 → 43,55 |

- История заказов выполнила 3 запроса вместо 22. Медиана времени драйвера снизилась со 159,13 до 23,02 мс, медиана остатка логики — с 19,80 до 7,01 мс. Сериализация заняла 0,163 и 0,140 мс при одинаковом теле в 2 459 байт.
- Рейтинг выполнил один SQL-запрос в обоих вариантах. Медиана SQL снизилась с 1 491,04 до 679,54 мс при одинаковом теле в 1 674 байта. Изменение времени пришлось главным образом на запрос. Медиана сериализации составила около 0,09 мс в обоих вариантах.
- На той же странице keyset сократил время драйвера с 19,18 до 7,94 мс. Транспортный остаток составил 15,55 и 15,34 мс соответственно. Его значение включает работу клиента и Uvicorn.
- Прогретый `top-products` на той же конфигурации дал **p50 27,81 мс**, `p95 89,06 мс` и `p99 92,91 мс`. Все 20 попаданий вернули тот же JSON с нулём SQL. Медиана этапа кэша составила 9,26 мс. [Профиль Redis HIT](../benchmarks/results/fastapi-medium-2026-11-24/cache.json)
- В микрозамере на одинаковой выборке из 1 000 пользователей медиана клиентской обработки составила 20,02 мс с ORM и 16,37 мс с Core. [Повторы ORM и Core](../benchmarks/results/fastapi-medium-2026-11-24/orm.json)

Медианы этапов вычисляются независимо по каждому столбцу. Сумма медиан может отличаться от медианы полного запроса.

## Пул соединений и workers

PostgreSQL сообщил `max_connections=100`, из них три зарезервированы. Конфигурации эксперимента использовали максимум два слота приложения. В строке с коротким таймаутом p50 рассчитана по пяти успешным ответам. [Все выборки пула и сведения о лимите](../benchmarks/results/fastapi-medium-2026-11-24/pool.json)

| Пул на worker | Workers | Таймаут | HTTP p50 успешных, мс | Получение соединения p50, мс | `503` |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 + 0 overflow | 1 | 2 с | 441,96 | 247,64 | 0 из 20 |
| 2 + 0 overflow | 1 | 2 с | 163,39 | 55,49 | 0 из 20 |
| 1 + 1 overflow | 1 | 2 с | 183,59 | 53,89 | 0 из 20 |
| 1 + 0 overflow | 1 | 40 мс | 115,71 | 9,54 | 15 из 20 |
| 1 + 0 overflow | 2 | 2 с | 248,28 | 137,90 | 0 из 20 |

При равном суммарном лимите в два соединения вариант с двумя workers показал более высокую медиану ожидания. По заголовкам подтверждены ответы обоих процессов. В режиме 40 мс все 15 ответов `503` завершились на получении соединения с нулём SQL. Эти результаты относятся к данному запросу продаж и локальной конфигурации.

## Воспроизведение

Запустите лабораторию с подготовленным `medium` и используйте новый каталог результатов. Сценарий `pool` переключает конфигурации сервиса API и по завершении возвращает настройки Compose из исходного окружения. Для последнего прогона кэш включается отдельно.

```bash
export API_PROFILING_ENABLED=true LAB_MODE=true ANALYTICS_CACHE_ENABLED=false
export WEB_CONCURRENCY=1 DB_POOL_SIZE=5 DB_MAX_OVERFLOW=5 DB_POOL_TIMEOUT=5
export ANALYTICS_CACHE_NAMESPACE=profile-benchmark
results=benchmarks/results/fastapi-local
docker compose up --build -d --wait
uv run --locked python -m scripts.profile_fastapi --scenario latency --output "$results"
uv run --locked python -m scripts.profile_fastapi --scenario orm --output "$results"
uv run --locked python -m scripts.profile_fastapi --scenario pool --output "$results"
ANALYTICS_CACHE_ENABLED=true docker compose up -d --wait
ANALYTICS_CACHE_ENABLED=true uv run --locked python -m scripts.profile_fastapi --scenario cache --output "$results"
```

Для просмотра профиля одного запроса в запущенном лабораторном режиме используйте следующую команду.

```bash
curl -i 'http://127.0.0.1:8008/api/v1/optimized/users/1/orders?limit=20'
```
