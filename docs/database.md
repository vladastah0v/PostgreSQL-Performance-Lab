# Схема PostgreSQL

Ревизия Alembic `0001` создаёт исходную схему для сравнения производительности.

| Таблица | Назначение и связи |
| --- | --- |
| `users` | Пользователи. Один пользователь может иметь несколько заказов и событий. |
| `categories` | Категории товаров с уникальным `slug`. |
| `products` | Товары с уникальным `sku`, каждый относится к одной категории. |
| `orders` | Заказы покупателей. Заказ объединяет позиции, платежи и историю статусов. |
| `order_items` | Позиции заказа со ссылкой на товар, количеством и ценой на момент покупки. |
| `payments` | Платежи. У заказа может быть несколько попыток оплаты. |
| `user_events` | События пользователя с полезной нагрузкой в `JSONB`. |
| `order_status_history` | Записи о переходах между статусами заказа. |

## Ключи и типы

- `BIGINT GENERATED BY DEFAULT AS IDENTITY` занимает 8 байт и даёт достаточный диапазон для миллионов записей. PostgreSQL выдаёт последовательные ключи, а режим `BY DEFAULT` позволяет задавать их явно при пакетной загрузке. После загрузки явных ключей последовательности нужно синхронизировать. [Числовые типы PostgreSQL](https://www.postgresql.org/docs/16/datatype-numeric.html)
- `NUMERIC(14, 2)` хранит денежные суммы с фиксированной точностью. Ограничения допускают нулевую стоимость и отклоняют отрицательные суммы и `NaN`.
- Временные поля имеют тип `TIMESTAMPTZ`. База и соединения приложения настроены на UTC. `created_at`, `updated_at` и `changed_at` получают серверное значение по умолчанию. SQLAlchemy обновляет `updated_at` у пользователей и заказов при изменении через ORM. При прямом SQL-обновлении это поле задаёт сам запрос.
- `users.country` хранит двухбуквенный код в верхнем регистре. `user_events.payload` хранит JSON-объект и по умолчанию равен `{}`.

## Статусы и целостность

| Сущность | Допустимые статусы |
| --- | --- |
| Пользователь | `active`, `inactive`, `blocked` |
| Заказ | `pending`, `paid`, `shipped`, `delivered`, `cancelled`, `refunded` |
| Платёж | `pending`, `paid`, `failed`, `refunded` |

PostgreSQL проверяет статусы через `CHECK`. Для платежей в статусе `paid` или `refunded` обязательна дата `paid_at`. Для начальной записи в истории заказа `old_status` может быть `NULL`. В остальных записях предыдущий и новый статусы должны различаться. Внешние ключи запрещают удаление записей, на которые остались ссылки. ORM-запросы загружают связи явно.

## Индексы исходной схемы

В исходной схеме `0001` 11 индексов. Восемь обеспечивают `PRIMARY KEY`, три обеспечивают уникальность `users.email`, `categories.slug` и `products.sku`. Ревизия `0002` добавляет восемь индексов для запросов Optimized API. [Обоснование и измерения](optimization.md)

## Проверка схемы

После запуска Compose применить миграцию и сверить схему с ORM можно следующими командами.

```bash
docker compose exec api alembic upgrade head
docker compose exec api alembic check
```

Интеграционные тесты используют мигрированную тестовую БД из `TEST_DATABASE_URL`. Для сервиса Compose с настройками по умолчанию команда выглядит так.

```bash
TEST_DATABASE_URL=postgresql+asyncpg://lab:lab-local-password@127.0.0.1:55432/performance_lab \
  uv run --locked pytest tests/integration
```
