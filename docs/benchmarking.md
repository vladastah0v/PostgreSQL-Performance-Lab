# Нагрузочное тестирование Locust

Нагрузочный сценарий `all` охватывает восемь GET-маршрутов. В него входят поиск пользователей, история покупателя, список заказов, детали заказа, продажи, рейтинг товаров, статистика клиентов и события. Каждый виртуальный пользователь повторяет тот же цикл с фиксированными параметрами. Стартовая позиция зависит от номера пользователя, а между вызовами добавляется пауза 100 мс. Перед прогоном скрипт сверяет JSON обоих вариантов на каждом выбранном маршруте. [Сценарии](../benchmarks/scenarios/analytics.py)

## Параметры запуска

- `--scenario` выбирает `all` или один маршрут. `--dataset` проверяет фактический набор по манифесту PostgreSQL.
- `--profiles` задаёт уровни `low`, `medium`, `high` и `stress` с 10, 50, 100 и 200 пользователями. `--users` задаёт произвольный список уровней до 200 пользователей. `--spawn-rate` управляет скоростью запуска.
- `--warmup` задаёт время прогрева после разгона. `--duration` ограничивает измеряемое окно. `--max-requests` ограничивает число отправленных запросов в этом окне. `--request-timeout` задаёт таймаут чтения HTTP.
- `--repetitions` задаёт число парных повторов. `--output` выбирает новый каталог отчёта.

Проверяется опубликованный локальный порт Compose, настройка `LAB_MODE=true` и выключенный Redis-кэш. Для теста используется одна схема PostgreSQL и одинаковое число воркеров Uvicorn. Перед каждым прогоном скрипт проверяет отсутствие активных клиентских сессий в целевой БД. Locust дожидается завершения запросов прогрева, открывает измеряемое окно и перестаёт отправлять запросы по истечении времени или достижении лимита. Уже начатым запросам предоставляется ограниченное время на завершение. В первом повторе раньше запускается Baseline, во втором — Optimized. PostgreSQL и Docker между прогонами продолжают работу, поэтому буферы PostgreSQL и файловый кэш ОС сохраняются. [Запуск Locust из Python](https://docs.locust.io/en/stable/use-as-lib.html)

## Метрики и артефакты

`rps` — завершённые запросы в секунду, включая HTTP-ошибки. `successful_rps` учитывает успешные ответы. Доля ошибок считается от числа отправленных запросов и включает HTTP-ошибки, сетевые ошибки и прерванные измерения. Квантили и средняя задержка берутся из завершённых вызовов, в том числе завершившихся ошибкой. Пропускная способность указывается по размеру тел ответов, которые получил HTTP-клиент, в байтах в секунду. Для RPS и пропускной способности используется измеренное время с завершением незаконченных запросов.

На каждом повторе сохраняются конфигурация, журнал Locust, сырые HTTP-измерения, срезы CPU и памяти контейнеров и генератора нагрузки, а также число клиентских соединений PostgreSQL. Контейнеры измеряются через `docker stats`, PostgreSQL через `pg_stat_activity`. `comparison.csv` содержит результаты каждого повтора по операциям и в целом. В `summary.csv` префикс `median_` обозначает медиану значений по повторам, а `spread_` — разность между наибольшим и наименьшим значениями, если доступно хотя бы два. Например, `median_p95_ms` показывает медиану p95 отдельных повторов.

## Результаты от 24 ноября 2026 года

Локальный Docker Desktop с 2 vCPU и 5,76 ГиБ RAM. Набор `medium` с `seed=42` содержит 10 000 пользователей, 100 000 заказов и 500 000 событий на ревизии `0002`. API работал с одним воркером и пулом `5 + 5`, Redis-кэш был выключен. Оба варианта вернули одинаковый JSON для всех восьми операций при предварительной проверке. [Метаданные запуска](../benchmarks/results/locust-medium-2026-11-24/metadata.json)

Для каждого уровня выполнено по два прогона каждой версии. После разгона Locust прогревал API 2 секунды и отправлял измеряемые запросы в течение 10 секунд. На 50 пользователях в первом повторе Baseline ошибок не было, во втором четыре запроса завершились HTTP 503 (2,37%). Optimized получил один `ConnectionError` (0,40%) и один HTTP 503 (0,46%) в разных повторах. Журнал API связал HTTP 503 с таймаутами ожидания соединения из пула. Ещё один такой таймаут Optimized произошёл при прогреве. [Результаты всех повторов](../benchmarks/results/locust-medium-2026-11-24/comparison.csv)

Во всех 12 прогонах наблюдалось до 10 клиентских соединений PostgreSQL, исключая соединение сборщика. Максимальный наблюдавшийся расход памяти API — 152,2 МиБ, PostgreSQL — 245,5 МиБ. На прогон пришлось 3–5 замеров ресурсов. В показаниях CPU `docker stats` встречались значения выше номинальной квоты контейнера. Результаты описывают короткие локальные прогоны с фиксированными фильтрами. [Срезы ресурсов и запросов](../benchmarks/results/locust-medium-2026-11-24/)

## Воспроизведение

С подготовленным набором `medium` запустите API в лабораторном режиме. Параметры пулов и workers берутся из конфигурации Compose. Сценарий сохраняет метаданные Docker Desktop и проверяет лимит подключений PostgreSQL перед нагрузкой.

```bash
LAB_MODE=true ANALYTICS_CACHE_ENABLED=false API_PROFILING_ENABLED=false API_METRICS_ENABLED=false WEB_CONCURRENCY=1 \
  docker compose up --build -d --wait

uv run --locked python -m scripts.run_benchmarks \
  --scenario all --dataset medium --users 10 25 50 \
  --duration 10 --warmup 2 --repetitions 2 \
  --max-requests 1000 --request-timeout 10
```

Для отдельной операции можно указать `--scenario top-products --profiles low`. По умолчанию папка результатов имеет вид `benchmarks/results/locust_<UTC timestamp>`.
