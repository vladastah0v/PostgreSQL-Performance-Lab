# Optimized API

Префикс `/api/v1/optimized` доступен в штатном режиме приложения. Он использует те же восемь маршрутов, бизнес-правила и схемы ответов, что и [Baseline API](baseline-api.md). По умолчанию списки принимают `limit` и `offset` с той же семантикой.

## Изменения запросов

- Поиск пользователей и список заказов выбирают только колонки, используемые в ответах. Списки и аналитика сравнивают `created_at` с границами UTC. Верхняя граница охватывает весь календарный день `date_to`.
- История заказов читает идентификаторы позиций одним пакетным запросом через `selectinload`. Детали загружают платежи через `joinedload`, позиции через `selectinload`. Это ограничивает дублирование строк от соединения двух коллекций. [Стратегии загрузки SQLAlchemy](https://docs.sqlalchemy.org/en/21/orm/queryguide/relationships.html)
- Рейтинг сначала агрегирует позиции по `product_id` и выбирает верхнюю часть рейтинга, затем получает названия товаров. Статистика клиентов группирует только подходящие заказы по пользователям и отдельно считает всех пользователей.

## Индексы Alembic `0002`

| Индекс | Запрос, который его использует |
| --- | --- |
| `ix_users_city_status_id` | Поиск по городу и выборочному статусу с сортировкой по ID. |
| `ix_orders_created_id` | Последние заказы и курсор по дате и ID без фильтра статуса. |
| `ix_orders_status_created_id` | Заказы заданного статуса в диапазоне дат, в том числе при глубокой пагинации. |
| `ix_orders_user_created_id` | История заказов одного пользователя. |
| `ix_order_items_order_id_id` | Пакетная загрузка ID позиций и выборка позиций заказа. |
| `ix_payments_order_id_id` | Платежи в деталях заказа. |
| `ix_user_events_user_created_id` | События пользователя по дате и ID. |
| `ix_orders_sales_created_cover` | Продажи и статистика клиентов. Частичный B-tree содержит только учитываемые статусы, `INCLUDE` покрывает сумму и ID пользователя. |

Для частичного индекса SQLAlchemy выводит фиксированные статусы продаж как SQL-литералы. PostgreSQL может сопоставить предикат запроса с предикатом индекса в подготовленном плане. Пользовательские значения передаются параметрами. На `medium` PostgreSQL выбрал `Index Only Scan` для аналитики продаж и клиентов. Сохранённые планы показывают 699 обращений к таблице для проверки видимости строк в каждом запросе. Для широкого поиска `Alex` в `New York` PostgreSQL выбрал первичный ключ, а для `Osaka` со статусом `blocked` выбрал функциональный индекс по городу и статусу. [Частичные индексы PostgreSQL](https://www.postgresql.org/docs/16/indexes-partial.html), [покрывающие индексы](https://www.postgresql.org/docs/16/indexes-index-only-scans.html)

Ревизия создаёт индексы обычным `CREATE INDEX` в одной транзакции. Это позволяет применить весь набор атомарно в локальном запуске. В диагностическом прогоне восемь индексов заняли 46,2 МиБ. Размеры и время создания каждого индекса зафиксированы через `pg_relation_size` и `pg_stat_statements`. [Метрики индексов](../experiments/indexes/optimized-api.json)

## Курсорная пагинация

`cursor=start` включает keyset для поиска пользователей, списка заказов, истории заказов и событий. При `has_more=true` следующий курсор приходит в заголовке `X-Next-Cursor`. Для следующего запроса передайте его как `cursor` с теми же фильтрами. `offset` в теле страницы равен `0` в режиме курсора. Изменение фильтров, использование курсора на другом маршруте или ненулевого `offset` вместе с курсором возвращает `422`.

```bash
curl -i 'http://127.0.0.1:8008/api/v1/optimized/orders?cursor=start&status=delivered&limit=20'
```

На `medium` сравнили одну и ту же страницу из 20 доставленных заказов за 2025 год на глубине 8 000. Скрипт получил курсор предшествующей записи перед замерами и проверил равенство строк и их порядка. Медиана пяти `EXPLAIN ANALYZE` на ревизии `0002` составила 7,27 мс для `offset` и 0,09 мс для keyset. Это время выполнения SQL с уже известным курсором. Все повторы и планы сохранены в JSON. [Планы и замеры пагинации](../experiments/sql/optimized/initial-plans.json)

```bash
uv run --locked python -m scripts.explain_queries \
  --implementation optimized --pagination-offset 8000
```

## Стоимость записи

Выполнили по три прогона `INSERT` и `UPDATE` на 1 000 сгенерированных заказов с `ROLLBACK` после каждого запроса. На той же БД `medium` медиана `INSERT` выросла с 24,86 мс на `0001` до 72,32 мс на `0002`, медиана `UPDATE` статуса выросла с 10,86 до 36,25 мс. Метрики описывают этот локальный сценарий и включают выполнение запроса PostgreSQL. [Все повторы и объём WAL](../experiments/indexes/optimized-api.json)

Для воспроизведения используйте мигрированные лабораторные базы с одним и тем же набором `medium` и ревизиями `0001` и `0002`. Выполните три прогона на каждой базе.

```bash
docker compose exec -T postgres sh -ec \
  'psql -X -qAt -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' \
  < experiments/indexes/orders-write.sql
```
